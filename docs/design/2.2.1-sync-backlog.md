## 2.2.1 sync

- **LOW: "Keep aside" for the held set pushes this phone's dirty settings under the household name.**
  When the household pair belongs to a set held as a question and the person answers "Not mine, keep
  them aside", the hold is released through the settings precedence (`releaseHousehold`). If this
  phone's settings are dirty (a real local edit), `.local` wins and the next push writes this phone's
  `GoalSettings-household` / `TaxProfile-household` over the other set's pair, under this phone's id.
  The other set's phones then ignore that pair (its owner is a held-apart set there), so nothing is
  lost, but the household pair name now carries this phone's values. Candidate fix: on "aside", mark
  the pair as another set's (`householdForeign`) instead of claiming it, and carry this phone's
  settings in its mirror pair only.

- **Settings of a set kept beside another set's household pair (verifier MEDIUM at caf41ea, fixed
  in 2.2; remaining behaviour noted here).** When the zone's household pair belongs to another set
  (`householdForeign`: a set kept with a new iCloud after P13, or another person's set whose records
  hadn't reached the zone at S5), this set never writes or applies that pair. Its goal and tax
  settings travel only in its own mirror pair, `GoalSettings-<id>` / `TaxProfile-<id>`. A set
  whose id was the literal `household` (which can't have a mirror pair) now takes a fresh
  `household-<8 hex>` id first, so its settings always reach iCloud. A household pair this phone
  wrote itself (matched against its push baseline, e.g. read back after a `changeTokenExpired`
  loop to S5) is never treated as another set's.
  Remaining for 2.2.1: a new phone on that iCloud reads the household pair (the other set's) as the
  settings to follow, not the mirror pair of the set it ends up with; and `householdForeign` is
  never cleared, even if the two sets are later combined. Both leave records untouched; the
  settings shown can be the other set's until edited.
